# HAKAISHA — 破壊者レビュー

AI は放っておくと褒める。褒めても成果物は強くならない。
このスキルは「褒めるな、壊せ」を工程として固定するもの。

## 原則

- **褒め禁止。** 良いところ探しから始めない
- **同一コンテキストの自己批判は甘くなる。** 自分が書いたものは自分の前提に引っ張られる。
  → **Agent ツールで別コンテキストを起動**し、成果物と受け入れ条件（＝何を満たせば合格か）だけを渡す。
  会話の経緯・言い訳・「こういう意図で」は渡さない。渡すと擁護される
- **モデル**: 日常は inherit。リリース級コード・公開物・不可逆な判断は上位モデルへ格上げする
- **ブリーフの秘密スクリーニング**: サブエージェントに渡す文面から、資格情報・個人情報・第三者の実名を落とす。
  「該当ディレクトリを Read させない」ところまで指定する

## 定型テンプレ

そのままサブエージェントに渡す。

### コード

```
high effort で敵対的コードレビュー。褒めない。
角度: ①正しさ（境界値・null・型・日跨ぎ等のドメイン例外） ②既存挙動の破壊
③セキュリティ ④パフォーマンス ⑤仕様と実装の乖離 ⑥実運用・実際の使われ方との乖離。
recall 優先で候補を広く挙げてから、各候補を実コードで検証して確度で絞る。
出力は上限 10 件、severity 順。各件: 現象 / 該当箇所 / 壊れる具体シナリオ / 修正案。
問題が見つからなければ「見つけられなかった」とだけ言う。埋め草の指摘をしない。
```

最後の2行が重要。これが無いと「特に問題ありません、強いて言えば命名が…」という
無害な指摘で枠を埋めにくる。

### 文章・企画・資料

角度を差し替える。

```
敵対的レビュー。褒めない。
角度: ①冒頭で続きを読みたくなるか ②強いが嘘っぽい断定 ③反論の先回りができているか
④弱い具体例 ⑤どこがAIっぽいか ⑥どこが退屈か ⑦読者が離脱・破綻するポイント
⑧削る箇所 ⑨足す箇所。
出力: 致命傷 / 弱点 / 削る / 足す / 書き換え案 / 再採点。
埋め草の指摘をしない。
```

### 判断・壁打ち

**「あえて反対する側」**として起動する。

```
私が採用しかけている案に、あえて反対する立場でレビューして。
突くところ: 最悪シナリオ / 撤退条件の穴 / 見えていない選択肢 / 前提が崩れる条件。
結論の代行はしない。判断材料を構造化して返す。
```

## 出力形式と収束

**致命傷 / 弱点 / 削る / 足す / 書き換え案 / 再採点（受け入れ条件比）。**

再採点が合格ラインに届くまで、生成⇔破壊を往復する。最低1往復。公開物・リリース物は2往復以上。

**2周回しても同じ根本欠陥を指摘し続けるなら、それはモデルの限界ではなく設計の限界のサイン。**
手直しでなく作り直しを検討する。

## 効く根拠

普通のレビューは「実装が仕様どおりか」を見る。破壊者は「**仕様のほうが間違っている**」を見つける。

実例: スコアの上限が固定されていたせいで、実行不能なプランに `isVerified: true` が付く
バグを発見した。通常のコードレビューでは、各関数は仕様どおりに動いていたので出てこない。
「楽観方向に嘘をつく前提の誤り」は、敵対的に読まないと見えない。
