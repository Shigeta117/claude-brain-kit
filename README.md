# claude-brain-kit

**Claude Code を「秘書」として運用するための、実測から作ったスキル集と brain テンプレート。**

半年ほど個人の全作業を Claude Code に通し、セッション履歴を採掘して
「口頭で3回以上繰り返した指示」「手で2回以上貼ったプロンプト」だけをスキル化したもの。
思いつきで作った理想論ではなく、**実際に毎回やっていたことの定型化**。

日本語で書かれている。

---

## まず1本だけ試すなら

**`skills/hakaisha`（破壊者レビュー）** から入るのが一番効果が分かりやすい。

AI は放っておくと褒める。褒めても成果物は強くならない。
このスキルは「褒めるな、壊せ」を別コンテキストのサブエージェントに投げる型で、
特に効くのは「**各関数は仕様どおりに動いているが、仕様のほうが間違っている**」類の欠陥。
普通のコードレビューでは絶対に出てこない。

```bash
mkdir -p ~/.claude/skills
cp -r skills/hakaisha ~/.claude/skills/
```

置いたら `claude` を起動して「これ壊して」と言うだけ。

---

## 導入

スキルは1つ１ディレクトリ、中身は `SKILL.md` 1枚。依存も設定もない。

```bash
# 全部入れる（どのプロジェクトでも有効）
mkdir -p ~/.claude/skills && cp -r skills/* ~/.claude/skills/

# プロジェクト単位で入れる（そのリポジトリでだけ有効）
mkdir -p <your-project>/.claude/skills && cp -r skills/mobile-web-check <your-project>/.claude/skills/
```

frontmatter の `description` が**発動条件**になる。会話の内容がそこに書かれた状況に当たると
Claude が自分で読みに来る。発動しないときはまず description のトリガー語を疑う。

## 収録スキル

| スキル | 何をするか | 効くとき |
|---|---|---|
| **hakaisha** | 褒めない敵対的レビュー。コード/文章/判断の3テンプレ | リリース・公開・提出の直前 |
| **overdrive** | 重量判定 → 勝利条件 → 3案 → 破壊 → 仕上げ の制作プロトコル | 成果物や重い判断を伴う依頼 |
| **mobile-web-check** | モバイルWeb/PWA の技術チェックリスト | スマホ向け画面を作る前・レビュー時 |
| **transitions** | UIモーションのトークン規律（MIT © Jakub Antalík） | 「全部300ms ease-in-out」を脱するとき |
| **shimai** | セッションの仕舞い。成果の振り分け→記録→索引→残ボール | 「今日はここまで」のとき |

### 中身の要点

**hakaisha** — 同一コンテキストの自己批判は自分の前提に引っ張られて甘くなるので、
成果物と受け入れ条件だけを別コンテキストに渡す。会話の経緯や「こういう意図で」は渡さない。
テンプレの末尾にある「**問題が見つからなければ見つけられなかったとだけ言う。埋め草の指摘をしない**」
の2行が効く。これが無いと無害な指摘で枠を埋めにくる。

**overdrive** — 全依頼に儀式を回すとただの遅いAIになるので、まず**重量判定**する。
判定は長さではなく**結果の重大性**で決める（短くても不可逆・高コストならフル圏）。
核は「**1案目は必ず最も無難な案になる。無難な案は弱い**」＝3案出してから殺す、の一点。

**mobile-web-check** — 4プロジェクトで下記が**すべて後追い修正になった**実測から逆算。
iOS の input font-size 16px 問題、`input[type=date]` のはみ出し、SW更新検知、
再取得でソート順が飛ぶ、無料枠の呼び出し量。どれも実装時なら3分。

**transitions** — [transitions.dev](https://github.com/Jakubantalik/transitions.dev) の
トークン体系と推敲規律の日本語版。**開閉は非対称**（modal open 250ms → close 150ms）、
**close にバウンス禁止**、**close と hover-out に遅延禁止**。
CSS本体は原典にあるので、実装時は原典を Fetch して逐語で取り込む。

**shimai** — セッションの終わりは一番情報が濃く、一番失われやすい。
記録は要約ではなく**決定と理由**を書く。何をしたかは差分を見れば分かるが、なぜそうしたかは
どこにも残らない。

## brain テンプレート

`brain-template/` は、**Claude に自分の文脈を持たせるための Markdown リポジトリ**の骨組み。

判断基準・プロジェクトの経緯・決定ログを1ディレクトリに貯め、そこを作業ディレクトリとして
Claude Code を起動する。同じ前提を毎回説明し直すのをやめるための仕組み。

肝は中身ではなく構造で、

1. `CLAUDE.md` が**ルーター**（全部を毎回読ませない。「何がどこにあるか」だけ書く）
2. `CONVENTIONS.md` が**書き込み規約**（AIに書かせるので、権限レベルを3層に分ける）
3. 各ディレクトリの `README.md` が**索引**（索引に無いファイルは次のセッションで発見されない）

の3点。作り方と運用の罠は [brain-template/README.md](brain-template/README.md) に書いた。

**`CONVENTIONS.md` の権限レベル3層**が一番の勘所。全部を「確認してから」にすると記録が溨まらず、
全部を「自由に書いてよい」にすると、AIが要約した「本人はこう考えている」が本人の判断基準として
定着し、以後その AI は存在しない判断基準に従って助言してくる。

  他人の環境では動かない
