# CONVENTIONS — brain への書き込み規約（エージェント向け）

> **ファイルを追加・編集する前に必ず読む。** CLAUDE.md が「何がどこにあるか」なら、
> こちらは「**何を、どこに、どう書くか**」。

## 1. どこに書くか（振り分け表）

| 内容 | 置き場所 | 命名 |
|------|---------|------|
| 判断基準・価値観・癖・文体 | `judgment/` | テーマ単位（`product.md`, `invest.md`） |
| 分析の元になった一次資料 | `judgment/sources/` | 資料名がわかる名前。**第三者は匿名化してから保存** |
| プロジェクトの事実・構成・経緯 | `projects/<name>.md` | プロジェクト名（小文字） |
| できごと・決定・インシデント・学び | `log/YYYY-MM-DD-<slug>.md` | 日付＋内容スラッグ |
| セッションをまたぐ作業の引継ぎ | `log/<slug>-todo.md` | 完了したら本文冒頭に完了と明記 |
| デバイス・環境・サブスク | `life/` | テーマ単位 |
| インフラ・ストレージ・ツール構成 | `SYSTEM.md` | — |
| 住所・会員番号など準機密 | **書かない**（別の非同期領域へ） | — |
| パスワード・APIキー | **絶対に書かない**（パスワードマネージャ） | — |
| 未整理の雑多メモ | `inbox.md`（直下） | 棚卸しで各所へ移動後、削除 |

迷ったら: ①各ディレクトリの README（索引）を見て近いものを探す → ②なければ新規ファイル →
③それでも迷うなら本人に聞く。

### コードプロジェクトの改善ネタは GitHub issue に起票する

背景: 改善ネタを `projects/<name>.md` に書き溨めると GitHub issue と二重管理になり、
どちらが最新か分からなくなる。
**issue は状態（open/close・ラベル・PRとの相互リンク）を持つが .md は持たない。
状態を持つものは issue に寄せる。**

| 置き場所 | 置くもの |
|---|---|
| **GitHub issue** | やること。背景・再現手順・受け入れ条件まで**詳細を全部書く** |
| **リポジトリの `docs/`** | 設計判断と却下理由。プロジェクト内で完結するもの |
| **brain `projects/<name>.md`** | 横断で効く文脈。他プロジェクトに跨る／そのプロジェクトが存在する理由 |

brain 側に issue を書くときの形式は `[owner/repo#123] 一行の主題 — 判断の要点`。
**番号だけにしない。** 番号だけだと、聞かれるたびにエージェントが `gh` を叩かないと何も答えられない。
一行あればその場で返せる。

**全 issue を鏡写しにしない。** brain に載せるのは「横断で意味があるもの」と
「判断を保留しているもの」だけ。純粋な実装タスクは issue にだけ置く。

### 一時ファイルは brain に置かない

検証・デバッグの途中で作る画像やスクリプトは brain に置かない。
セッションの scratchpad ディレクトリを使う。

背景: 検証スクショット3枚（計485KB）が直下に落ちたまま3日滞留し、git にも追跡されていた。
誰も参照していないので次に読むエージェントには由来が分からず、削除の判断もできない。

brain に残す価値がある画像は、**必ず該当フォルダの中に置き、Markdown から参照する。**

## 1.5 プロジェクトが複数ファイルに育ったとき

背景: あるプロジェクトがフラット9ファイル・75KBの一枚岩に育ち、
**引用の所在をAIが拾い損ねる実害**が出た。検索性の低い構成は蓄積を無駄にする。

- **3ファイル超えたらサブディレクトリ化**: `projects/<name>/` を作り、入口に README.md
  （役割マップ: どのファイルに何があるか・読む順）を必ず置く
- **1ファイル1役割**: 運営情報／構想・論点／資料・引用／進捗ログ のように役割で分ける。
  1ファイルが50KBを超えたら分割を検討
- **正本を常に1本明示する**: 最新形を正本として README に明記し、旧世代は `archive/` へ移す。
  **削除はしない**（過去の記述・引用が資産になる）
- **ファイル冒頭に役割１行**: H1直下に「役割: …。関連: [[…]]」
- **移動・改名時はリンク総点検**: `grep -rn "旧名" --include="*.md"` で張り替えてから完了とする

## 2. 書き込みの権限レベル（最重要）

| 対象 | ルール |
|------|--------|
| `judgment/` | 本人に関する解釈・確定は **本人の確認を取ってから**。会話中に明示承認された内容はその場で追記可。未承認の下書きは冒頭に `⚠️未レビュー` を付け、確認が取れたら `レビュー反映済み・YYYY-MM-DD` に差し替える |
| `projects/` `log/` `life/` | 客観的事実の記録はエージェント判断で追記してよい。**ただし出典と日付を残す** |
| `CLAUDE.md` `SYSTEM.md` 本ファイル | 構造・ルールの変更は提案してから（軽微な実態追従は可。変更内容を報告する） |

**この3層があることが肝。** 全部を「確認してから」にすると記録が溨まらず、
全部を「自由に書いてよい」にすると本人の考えていないことが本人の判断基準として定着する。

## 3. ファイルの型

- 冒頭に H1 ＋ 1〜2行の要約。鮮度が重要なファイルは `最終更新: YYYY-MM-DD` を明記
- **出典を書く**（一次資料名／「本人の発言 YYYY-MM-DD」等）。**推測と確認済み事実を区別する**
- **相対日付を使わない**（「先週」→ `2026-06-25`）
- 判断・却下を記録するときは**理由と再評価のトリガー**まで書く
- 関連ファイルは `[[name]]` または相対リンクで相互接続する
- エージェントの要約から「具体的で検証可能な事実」を書くときは、**一次資料まで遡って裏取りしてから**書く

## 4. 索引の維持

`judgment/` `projects/` `log/` は各 `README.md` が索引。
**ファイルを追加したら必ず索引に1行追記する。**

索引に載っていないファイルは、次のセッションで発見されない。書いたのに使われない記録は、
書かなかったのと同じ。

## 5. 第三者情報・機密

詳細は CLAUDE.md。ここでは運用の線引きだけ。

- **業務上の共同開発者は実名可**（GitHub 等で公開されている協業関係のため）。
  ただし**機微文脈（トラブル・評価・健康）は実名可の相手でも伏せる**
- 私生活の同行者はあだ名で書く
- **クライアント側担当者・取引先・その他第三者はデフォルト匿名化**

## 6. 巨大化への対応

- 定期的に「50KB超のファイル」「索引に無いファイル」「参照されていない非Markdownファイル」を洗う
- **ファイルが肥大化したときは、コメント削除や圧縮で収めるのではなく責務分割を優先する**
